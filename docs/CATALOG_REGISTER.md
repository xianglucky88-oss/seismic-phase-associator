# 目录修订登记册

本登记册记录**目录版本**与**事件修订**。它是系统外的流程资产：当前代码不产生版本号、不产生修订链，也不保留被替换的结果（`DATA_CONTRACT.md` §8、§10）。

## 1. 为什么必须手工登记

当前系统的事实只有一条：**相同输入 → 相同输出**（确定性）。除此之外：

- 没有 `catalog_version` / `revision` / `supersedes` 字段 `[未实现]`；
- `event_id` 会因迟到 pick 或合并而重排 `[已钉住]`；
- 人工撤回只能通过「重放整份输入」表达，重放不留痕 `[已实现]`。

因此，**任何需要「这次发布相对上次改了什么」的能力，都必须由本登记册提供**。登记册是唯一权威，代码输出不是。

## 2. 版本标识规则

| 标识 | 格式 | 谁分配 | 说明 |
|---|---|---|---|
| `catalog_version` | `YYYYMMDD.N` | 发布负责人 | 每次对外发布一个；`N` 为当日序号，从 1 开始 |
| `run_key` | `sha256(规范化输入 JSON)` | 登记人 | **输入**指纹，用于证明两次结果是否同源 |
| `code_ref` | git commit SHA | 登记人 | 产生该版本的代码版本 |
| `engine_version` | 当前为 `0.1.0`（`pyproject.toml`） | 代码 | 与 `code_ref` 冗余，便于人工比对 |
| `event_ref` | `<catalog_version>:<event_id>` | 登记人 | 跨版本引用事件时的**复合键**，单独 `event_id` 永远不安全 |

> 规则：对外只允许引用 `event_ref`，禁止裸 `event_id`。这是 `DATA_CONTRACT.md` §8 结论的直接落地。

`run_key` 生成方式（规范化后取哈希，键排序、浮点统一 `repr`）：

```bash
python3 tools/run_key.py fixtures/scenarios/late_pick/before.json
```

> `run_key` 只覆盖 `JSON` 里实际存在的键（包括 `_note` 说明字段）。若某份输入含解释性注释，先移除注释再计算，否则注释变化会被误判为输入变化。

> 注意：`run_key` 证明的是**输入相同**，不能证明**代码相同**。两者必须同时登记。

## 3. 修订登记表（模板）

每次发布追加一行，不要修改历史行；更正以新增行的方式表达。

| rev | catalog_version | run_key (前 12 位) | code_ref | 变更摘要 | 受影响 event_ref | 影响类别 | 评审人 | 回滚点 |
|---|---|---|---|---|---|---|---|---|
| 1 | 20261117.1 | `__________` | `d021418` | 基线发布 | — | — | — | — |
| 2 | | | | | | | | |

**影响类别**（与 `SCENARIOS.md` 影响矩阵一致，可多选）：

- `T` 时间/原点变化（`origin_time`）
- `M` 事件成员变化（台站集 / `pick_count`）
- `I` 事件身份变化（`event_id` 重排、合并、拆分）
- `R` 未关联余额变化（`rejected_pick_count`）
- `S` 结构/契约变化（新增字段、语义变更、版本策略）

## 4. 事件级修订登记表（模板）

当同一物理事件在多个版本间存在时使用。由于没有稳定 ID，**必须**用「台站集 + 原点时间」作为人工锚点，并显式记录它是否变化。

| event_ref | 锚点（台站集 @ origin_time） | 前驱 event_ref | 变更 | 原因 | 复核结论 |
|---|---|---|---|---|---|
| | | | | | |

变更取值：`added` / `removed` / `retimed` / `membership_changed` / `merged_from` / `split_into` / `retracted`。

## 5. 登记时必须回答的责任问题

每条修订都要能回答下列问题，否则不予发布：

1. **拾取身份**：本次是否涉及重复投递或撤回？若是，凭什么证明不是新证据？（当前只能人工比对，见 `DATA_CONTRACT.md` §3）
2. **台站校正**：是否修改了 `clock_corrections`？若是，受影响的是「仅时间」还是「成员/身份」？（`SCENARIOS.md` §5）
3. **关联**：关联规则/窗口是否变化？变化后的受影响事件用 `tools/replay_diff.py` 列全。
4. **身份**：是否发生 `event_id` 重排？所有 `event_ref` 是否已重新登记？
5. **震级来源**：若发布震级，来源是什么？当前流水线不产生震级，若登记册出现震级，必须写明外部来源 `[未实现]`。
6. **未关联原因**：`rejected_pick_count` 变化时，能否说明是哪类拒绝？（当前只能定性，见 `DATA_CONTRACT.md` §7）

## 6. 版本策略变更的影响评审

当提出「引入 `catalog_version` 字段」「改变 `event_id` 生成规则」「新增 `confidence`」这类**策略**变更时：

1. 先判断它把哪些字段从 `[未实现]` 提升为 `[已实现]`（对照 `DATA_CONTRACT.md` 标签）。
2. 用 `tools/replay_diff.py` 对 `fixtures/scenarios/` 全量回放，生成前后差异清单。
3. 在 §3 表新增一行，`影响类别` 至少标 `S`，若同时改变结果则加标 `T/M/I/R`。
4. 在 §4 表登记被重排/合并/拆分的每个事件。
5. 明确回滚点（`REVIEW_AND_ROLLBACK.md` §4）。

## 7. 已知无法登记的情形（必须显式声明）

| 情形 | 为什么无法登记 | 缓解 |
|---|---|---|
| 相同输入、不同代码 | `run_key` 不含代码指纹 | 同时登记 `code_ref`；发布前 diff 代码 |
| 重复投递 vs 新相位 | 无 pick 身份 | 人工比对时间与台站；在备注中声明假设 |
| 被撤回 pick 的原值 | 重放不保留被删 pick | 归档**每次提交的完整输入**，而非只归档输出 |
| 事件被合并后的两段历史 | 无 `supersedes` | 在 §4 用工整的 `merged_from` 行手工维护 |
| 震级来源 | 流水线无震级 | 震级一律标注外部来源 |

> 归档要求：**保留每次提交的完整输入 JSON**，因为输出可由输入确定性重算，而被撤回的 pick、重复的 pick 一旦丢失输入就永久无法还原。
